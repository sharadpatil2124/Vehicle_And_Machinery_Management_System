 PART 1 — HOW TO USE THE TWO FILES
====================================================================================================

  ISSUE_TRACKER.md  = the control panel.
    - One table with every issue: severity, phase, order, status, result.
    - The decisions table where your answers are recorded.
    - The results log: one row per finished issue with its test numbers.
    - Updated by me after every issue. Short on purpose.

  ISSUE_DETAILS_AND_WORKFLOW.txt (this file) = the explanations.
    - Read an issue's section in PART 5 before assigning it.
    - Changes only when an issue's plan changes (noted in the tracker history).

    3. Give me the instruction (PART 3).

====================================================================================================
 PART 2 — THE WORKFLOW, STEP BY STEP
====================================================================================================

  Overview (one issue goes through steps 4 to 9; then the next issue starts):

    [0 Prepare] -> [1 Identify] -> [2 Prioritise] -> [3 Decide]
         -> [4 Assign] -> [5 Plan (optional)] -> [6 Implement] -> [7 Test]
         -> [8 Report + update tracker] -> [9 Your review + accept] -> next issue

----------------------------------------------------------------------------------------------------
 STEP 0 — PREPARE (once, before the first fix)
----------------------------------------------------------------------------------------------------
  0.1 Save your current work in git.
      Your working copy has 76 modified and 12 new files that are not committed (on branch
      "main"). If fixes are added on top of that, nobody can see or undo one fix by itself.
      Commit this work first (or ask me: "Commit current work"). Optionally create a branch for
      the fixes. I never commit unless you ask.

  0.2 Keep the tests in the project (task T-1).
      The 203 tests were written in a temporary session folder that can disappear. T-1 copies
      them into server/tests/ and adds an "npm test" command. No new packages are installed
      (Node's built-in test runner is used). Benefit: every fix is checked the same way, by me
      or by your partner, and later work can be checked too.
      Without T-1 I can still work, but I would have to re-create tests, which is slower.

  0.3 Test database (already ready).
      Tests run on a separate database, "vmms_unittest", built only from the repo migrations.
      Your development database "vmms" is never touched by tests.
      If a fix needs a migration, I apply it to vmms_unittest only and ask you before it is
      applied to "vmms" (vmms has known drift: 3 extra old migrations and orphan tables).

  0.4 Decisions.
      Some issues need a business choice first (tracker section 6). Answer them only when that
      issue comes up — not all at once.

 STEP 1 — IDENTIFY ISSUES
----------------------------------------------------------------------------------------------------
  How the current list was produced:
    - 11 automated test suites: pure functions, auth & users, tenant isolation & roles,
      sites & assets, inventory, fuel, tyres, maintenance/dashboard/branding, input fuzzing,
      concurrency (parallel requests), client contract & build.
    - A static check that every route calls a function that really exists.
    - Reading each service file and checking the client screens.
    - Every failing test was checked by hand: all 59 are real defects, not test mistakes.

  New issues found later:
    - If I discover a new problem while fixing an issue, I do NOT fix it. I add it to the
      tracker as the next ID (ISSUE-30, ...) with status "Open" and tell you in my report.
    - You can report one yourself: "Add issue: <what you saw>". I investigate, write it up in
      both files, and wait.

----------------------------------------------------------------------------------------------------
 STEP 2 — PRIORITISE
----------------------------------------------------------------------------------------------------
  Four things decide the order:
    1. Severity — how much damage it does (Critical > High > Medium > Low).
    2. Reachable from the UI — can a normal user trigger it, or only an API call?
    3. Dependencies — some fixes must come before others (example: 01 and 05 before 02).
    4. Effort — small safe fixes first build confidence in the process.
  Result: five phases (PART 4). You may change the order at any time:
    "Move ISSUE-xx to phase N" or "Do ISSUE-xx next".

----------------------------------------------------------------------------------------------------
 STEP 3 — DECIDE (only for issues marked "Needs decision")
----------------------------------------------------------------------------------------------------
  - PART 5 lists the options with advantages and disadvantages, and my recommendation.
  - You answer, for example: "Decision 02: option A".
  - I record your answer in tracker section 6 and change the status to "Open".

----------------------------------------------------------------------------------------------------
 STEP 4 — ASSIGN ONE ISSUE
----------------------------------------------------------------------------------------------------
  - One issue per message, using a phrase from PART 3.
  - If you assign an issue that still needs a decision, I stop and ask the question first.

----------------------------------------------------------------------------------------------------
 STEP 5 — PLAN (optional; recommended for effort M and L)
----------------------------------------------------------------------------------------------------
  "Plan ISSUE-xx" -> I reply with:
    - the exact files I will change,
    - the behaviour before and after,
    - risks and side effects,
    - the tests I will run or add.
  No code changes. You answer "Go" (or adjust the plan).
  For small (S) issues you can skip this and say "Fix ISSUE-xx" directly.

----------------------------------------------------------------------------------------------------
 STEP 6 — IMPLEMENT
----------------------------------------------------------------------------------------------------
  Rules I follow:
    - Only the files needed for that issue. No unrelated clean-up, renaming or reformatting.
    - Same style as the surrounding code.
    - A new migration only if the issue's plan says so, after checking the next free number.
    - Client (frontend) changes only if the issue's plan lists them.
    - If the fix turns out bigger or riskier than described, I stop and tell you before going
      further.

----------------------------------------------------------------------------------------------------
 STEP 7 — TEST (details in PART 7)
----------------------------------------------------------------------------------------------------
  T1 the issue's own tests pass (the baseline failures mapped to it in tracker section 8,
     plus any new test written for it)
  T2 full regression on a freshly rebuilt test database: every test that passed before still
     passes, and the failure count drops by exactly this issue's tests
  T3 client build (if client code changed) and the wiring check
  T4 migration up / down / up (if a migration was added)
  T5 a short manual click-through for you (if the issue is reachable from the UI)
  If anything that passed before now fails, the fix is not finished. I correct it or undo it
  before reporting. A half-finished fix is never left in place.

----------------------------------------------------------------------------------------------------
 STEP 8 — REPORT AND UPDATE THE TRACKER
----------------------------------------------------------------------------------------------------
  My report always contains:
    - what changed (files) and the behaviour before -> after,
    - test numbers, e.g. "pass 147 / fail 56 — the 3 tests for this issue now pass,
      no regressions",
    - manual steps for you to try (if any),
    - anything new I noticed (added to the tracker as a new issue, not fixed).
  In the tracker I update: the status (-> "Fixed – verified"), the Result column, section 1
  (current status), and a new row in the results log (section 9).

----------------------------------------------------------------------------------------------------
 STEP 9 — YOUR REVIEW AND ACCEPTANCE
----------------------------------------------------------------------------------------------------
  - Check the change: look at the diff in VS Code's Source Control panel, and/or try the
    manual steps.
  - Then one of:
      "Accept ISSUE-xx"            -> status becomes "Closed"
      "Change ISSUE-xx: <what>"    -> I adjust and re-test
      "Revert ISSUE-xx"            -> I undo exactly that issue's changes and re-test
  - Optional: "Commit ISSUE-xx" -> one git commit containing only that issue's files.
  Then assign the next issue.

----------------------------------------------------------------------------------------------------
  Issues (order): 01, 05, 02 (+22), 04
  Goal          : stock quantities and values can never be posted twice or corrupted, and

  Why this order: today the numbering failures in ISSUE-02 accidentally stop some duplicate

  Advantages    : removes the only Critical issues; stock reports become trustworthy.

----------------------------------------------------------------------------------------------------
  Issues (order): 08, 07, 16, 10, 15b, 18, 19, 20, 21, 28

  Why here      : each is a small guard (a check that refuses a bad action). 07 needs your

  Advantages    : prevents new bad data; each fix is easy to test in isolation.
  Disadvantages : users get new "you can't do that because ..." messages where they used to
                  succeed. That's intended, but worth telling users.
  Risk          : low to medium. Existing bad data is not changed. SQL checks are provided to
                  find it.
  Done when     : all Phase 3 issues are Closed.

----------------------------------------------------------------------------------------------------
  Issues (order): 13, 11, 24
  Goal          : the browser always knows the user's current site; logout and password resets

  Advantages    : security hardening; fewer confusing errors for reassigned supervisors.
  Disadvantages : 11 needs a migration and changes logout behaviour (all devices).
  Risk          : medium for 11 (login flow); low for 13 and 24.

 ISSUE-01 — Receiving a purchase or stock transfer twice adds the stock twice
----------------------------------------------------------------------------------------------------
  Severity: Critical   Phase: 2 (1st)   Effort: M
  Modules: Inventory - Purchases, Stock transfers, Stock balances, Inventory reports,
           Dashboard (purchase totals)
  Reachable from the UI: yes, via two users, two browser tabs, or a network retry.
    (A single double-click is already blocked: the Receive button disables itself.)
  Depends on: nothing. Must be done before ISSUE-02.
  Baseline tests: 1 failing (transfer received 4 times). +1 test to add: purchase received
    3 times when the item already has stock (today that case looks safe by accident).
  Files likely to change: server/src/services/purchase.service.js,
                          server/src/services/stockTransfer.service.js

  WHAT HAPPENS
    - 3 simultaneous "receive" requests on a 10-unit purchase added 30 units.
    - 4 simultaneous receives of a 5-unit transfer moved 20 units out of the source site.

  CAUSE
    The "is it still draft / in transit?" check runs before the database transaction starts,
    and the purchase/transfer row is not locked. Every request passes the check, then every
    request posts stock.
      purchase.service.js:277      status check (the transaction starts at line 293)
      stockTransfer.service.js:240 same pattern
    (When the item has no stock row yet, the duplicates crash with a deadlock instead. That
    explains why some runs looked safe.)

  IMPACT
    Stock on hand, stock value and average cost too high. The stock register, purchase report
    and dashboard purchase totals are wrong from then on. Transfers drain the source site.

  RECOMMENDED SOLUTION — lock and re-check inside the transaction
    1. Inside the transaction, read the purchase again with a row lock (SELECT ... FOR UPDATE).
       If it is no longer "draft", return the existing 409 "already received" message.
       (Fuel collections already work this way: fuelCollection.service.js:266.)
    2. Read the purchase lines after the lock, inside the same transaction.
    3. Add the same lock and re-check to purchase editing, so edit and receive can't overlap.
    4. Same for stock transfer receive (lock, check "in_transit", then load the lines).

  ALTERNATIVES
    B. Atomic status switch: UPDATE ... SET status='received' WHERE id=? AND status='draft',
       and continue only if 1 row changed.
       + no waiting on a lock
       - stock is posted after the status is already flipped, so the logic needs care;
         slightly less obvious to read
    C. Client-side only (disable the button harder).
       + trivial
       - does not stop two users, two tabs, retries or API calls. Not a real fix.

  ADVANTAGES
    Closes the hole completely; small change; reuses a pattern already in the code.
  DISADVANTAGES
    A second simultaneous receive waits about a second for the first to finish (it then gets a
    clean 409).
  SIDE EFFECTS
    None visible in normal use. No API, UI or data-format change.
  DECISION
    None.
  DATA CHECK (rows returned = posted more than once)
    SELECT tenant_id, reference_id, COUNT(*) FROM inventory_transactions
     WHERE transaction_type='PURCHASE_RECEIPT' AND reference_type='PURCHASE_ITEM'
     GROUP BY tenant_id, reference_id HAVING COUNT(*) > 1;
    SELECT tenant_id, reference_id, COUNT(*) FROM inventory_transactions
     WHERE transaction_type='TRANSFER_OUT' AND reference_type='STOCK_TRANSFER_ITEM'
     GROUP BY tenant_id, reference_id HAVING COUNT(*) > 1;
  TESTING
    Parallel receive tests (purchase with existing stock: exactly +10; transfer: exactly 5
    moved, one 200 and the rest 409); full inventory suite; full regression.

 ISSUE-02 — Records created at the same time fail with deadlocks (auto-numbering)
----------------------------------------------------------------------------------------------------
  Severity: Critical   Phase: 2 (3rd)   Effort: L   Status: needs decision
  Modules: every numbered record —
    vehicles (VEH-), machinery (MCH-), item categories (CAT-), units (UOM-), items (ITM-),
    suppliers (SUP-), storage locations (LOC-), purchases (PO-), asset issues (ISS-),
    reversals (REV-), stock adjustments (ADJ-), transfers (TRF-), every stock movement (TXN-),
    fuel stations (FST-), fuel collections (FC-), tyre types (TT-), tyre purchases (TP-)
  Reachable from the UI: yes, any two users saving the same kind of record at the same time.
  Depends on: ISSUE-01 and ISSUE-05 first. Also fixes ISSUE-22.
  Baseline tests: 4 failing (parallel vehicles, items, issues of different items, last units)
  Files likely to change: a new migration (next free number was 0067 — re-checked before
    creating), server/src/services/codeGenerator.js, and the number generator in each of the 17
    services listed above.

  WHAT HAPPENS
    - 8 simultaneous vehicle creates: 1 succeeded, 6 "Deadlock found" (500), 1 "already in use".
    - Even 2 simultaneous vehicle creates always fail one.
    - 6 simultaneous parts issues for DIFFERENT items: only 1 succeeded.

  CAUSE
    Each new number is "highest existing number + 1", read inside the business transaction
    (codeGenerator.js:3, vehicle.service.js:41, inventoryTransaction.service.js:24, ...).
    - MySQL keeps showing a transaction the same snapshot, so the retry loop reads the same
      stale "highest number" 5 times.
    - Meanwhile the competing inserts take locks that deadlock each other.
    - Every stock movement takes a tenant-wide TXN- number, so even different sites collide.

  IMPACT
    Random "Internal server error" or "That value is already in use" when two people work at
    once. The whole save is lost and must be retried.

  RECOMMENDED SOLUTION — option A: a counter table, numbers allocated outside the transaction
    1. Migration: table tenant_sequences (tenant_id, name, value), with one row per organization
       per prefix.
    2. Seed the rows from today's highest NUMERIC value of each code. Numeric, not alphabetical:
       this also fixes ISSUE-22.
    3. One shared helper takes the next number in its own tiny statement that commits
       immediately (INSERT ... ON DUPLICATE KEY UPDATE value = LAST_INSERT_ID(value + 1)).
    4. Keep the formats exactly: PREFIX + 6 digits, which naturally grows to 7 after 999,999.
    5. Remove the 5-attempt retry loops; they are no longer needed.

  ALTERNATIVES
    B. Counter row locked inside the business transaction (gap-free numbers).
       + numbers never skip (PO-000041 always exists if PO-000042 does)
       - all creates of that type in an organization queue behind each other
       - every stock operation must lock the TXN counter first, or new deadlocks appear
       - more complex and slower under load
    C. Keep the generators, retry the whole transaction on deadlock or duplicate.
       + smallest code change
       - still fails under real load (retries collide again); slow
       - does not fix the 999,999 problem; hides the cause

  ADVANTAGES (option A)
    No locks held, no deadlocks, constant speed. Fixes ISSUE-22. One helper replaces 17 copies.
  DISADVANTAGES (option A)
    Numbers can skip when a save fails (like database auto-increment). Largest change in the
    list: a migration plus 17 places, so a careful test of each record type is needed.
  SIDE EFFECTS
    Possible gaps in numbering. Formats unchanged. No UI change.
    Duplicate postings in 01/05 become easier to hit — which is why 01 and 05 go first.
  DECISION
    Are gaps in reference numbers acceptable? (Recommended: yes -> option A.)
    If gap-free numbers are a legal or audit requirement -> option B.
  TESTING
    8 parallel creates of vehicles, items, purchases and asset issues (all succeed, all numbers
    unique); seeding test on a database that already has records (the next number continues);
    migration up/down/up; full regression.

----------------------------------------------------------------------------------------------------
  Severity: High   Phase: 1 (1st)   Effort: S
  Modules: Fuel reports, Inventory reports, Tyre reports
  Reachable from the UI: no. The report pages use the summary endpoints. API consumers (for
    example automation tests) get errors.
  Baseline tests: 3 failing
  Files likely to change: server/src/services/fuelReport.service.js,
    server/src/services/inventoryReport.service.js, server/src/services/tyreReport.service.js

  WHAT HAPPENS
    These routes crash every time with "... is not a function":
      GET /fuel-reports/collections/by-station   (fuelReport.controller.js:20)
      GET /fuel-reports/collections/by-carrier   (fuelReport.controller.js:25)
      GET /inventory-reports/purchases/by-supplier (inventoryReport.controller.js:15)
      GET /inventory-reports/purchases/by-item   (inventoryReport.controller.js:20)
      GET /tyres/reports/assets/tyres            (tyre.controller.js:74)
      GET /tyres/reports/costs/by-type           (tyre.controller.js:84)
      GET /tyres/reports/costs/by-supplier       (tyre.controller.js:89)

  CAUSE
    The controllers call service functions that were never written (git history has no
    version of them). The summary services already calculate the same data.

  IMPACT
    No UI impact today. Automation tests and any API user get 500 errors.

  RECOMMENDED SOLUTION — thin service functions that return slices of the existing summaries
    collectionsByStation -> collectionsSummary().byStation   (same for byCarrier)
    purchasesBySupplier  -> purchases().bySupplier            (same for byItem)
    costsByType          -> costReport().byType               (same for bySupplier)
    assetTyres           -> the fitments of one asset (assetType + assetId required), using
                            the existing fitment listing

  ALTERNATIVES
    B. Delete the 7 routes, their handlers, and the unused client API functions.
       + less code
       - removes API endpoints that the client code already declares; if a page needs them
         later, they must be rebuilt

  ADVANTAGES
    Tiny change; reuses tested calculations; same filters and site scoping as the summaries.
  DISADVANTAGES
    Slight duplication of endpoints (summary + slices).
  SIDE EFFECTS
    None for existing pages.
  DECISION
    None (option A recommended; say "with option B" to delete instead).
  TESTING
    Each route returns 200 with figures equal to the summary endpoint; supervisors still scoped
    to their site; the wiring check reports 0 problems; full regression.

 ISSUE-04 — Stock transfers can exceed stock, get stuck in transit, and can't be cancelled
----------------------------------------------------------------------------------------------------
  Severity: High   Phase: 2 (4th)   Effort: M
  Modules: Inventory - Stock transfers, Stock balances; client transfer form and detail page
  Reachable from the UI: yes (the transfer form doesn't check available stock)
  Baseline tests: 2 failing
  Files likely to change: server/src/services/stockTransfer.service.js, stockTransfer.controller.js,
    stockTransfer.routes.js, models/StockTransfer.js, a new migration (status "cancelled"),
    client/src/api/client.js, client/src/pages/inventory/StockTransferDetailPage.jsx

  WHAT HAPPENS
    - A transfer of 50 units was accepted with only 1 on hand.
    - Stock isn't reserved during transit, so it can still be issued at the source.
    - At receive time: "not enough stock", and there is no cancel. The transfer stays
      "in transit" forever.

  CAUSE
    stockTransfer.service.js:156 (create) only estimates the cost (line 176); it never checks
    quantity. There is no cancel route, and the status list has no "cancelled".

  IMPACT
    Stuck transfers in the lists; users re-create transfers to work around them; the stock
    picture is confusing.

  RECOMMENDED SOLUTION
    1. At dispatch, per item and source location (summing lines of the same item): require
       on hand - quantity already in other in-transit transfers from that location
       >= requested. Otherwise 400 with "available X, requested Y".
    2. At receive: keep the check, with a clearer message ("stock was used after dispatch —
       cancel this transfer or adjust stock").
    3. New: cancel an in-transit transfer (admin only, type DELETE to confirm). Status becomes
       "cancelled" (migration), with an audit entry. Nothing is posted to stock, because
       nothing was posted at dispatch.
    4. Client: a Cancel button on the transfer detail page; "cancelled" badge and filter.

  ALTERNATIVES
    B. Real reservation, using the existing unused reservedQuantity column.
       + reserved stock can't be issued by anyone
       - parts issues, stock counts and adjustments must all respect reservations: a
         wider change touching several modules
    C. Deduct stock at dispatch (OUT at dispatch, IN at receive).
       + stock is never "double available"
       - changes what the stock pages and register show for in-transit goods; reports need
         rework

  ADVANTAGES
    Blocks impossible transfers at the start; gives a clean exit for stuck ones; small,
    contained change.
  DISADVANTAGES
    Stock can still be issued at the source while in transit (only B prevents that). Receive
    then fails clearly and the transfer can be cancelled.
  SIDE EFFECTS
    Over-stock transfers are refused at dispatch; a new status "cancelled" appears in lists and
    the API.
  DECISION
    None (B or C only if you want them).
  DATA CHECK
    SELECT id, transfer_number, created_at FROM stock_transfers WHERE status='in_transit';
  TESTING
    Over-dispatch -> 400; two lines of the same item exceeding stock together -> 400; cancel works
    and is audited; a cancelled transfer can't be received; the normal path still moves stock at
    the oldest-first cost; migration up/down; client build.

 ISSUE-05 — Repeated lines over-reverse or double-adjust stock
----------------------------------------------------------------------------------------------------
  Severity: High   Phase: 2 (2nd)   Effort: M
  Modules: Inventory - Issue reversals, Stock adjustments (stock counts), Stock balances
  Reachable from the UI: stock count = yes (the form allows the same item twice);
    reversal = API only (the UI reverses one line at a time)
  Depends on: before ISSUE-02
  Baseline tests: 2 failing
  Files likely to change: server/src/services/issueReversal.service.js,
    server/src/services/stockAdjustment.service.js
    (optional: client/src/pages/inventory/StockAdjustmentFormPage.jsx)

  WHAT HAPPENS
    - One reversal listing the same issued line twice put back 4 units when only 2 were issued.
    - One stock count listing the same item twice with "counted 15" left the stock at 20.

  CAUSE
    Each line is checked against quantities read BEFORE any line is posted, and those reads
    happen outside the transaction:
      issueReversal.service.js:69     each line checked against "remaining" separately
      stockAdjustment.service.js:142  each line computes "counted - system" from the same start
    Two simultaneous reversals of one line can also both pass (today the second one is stopped
    only by the ISSUE-02 numbering crash).

  IMPACT
    Stock and value too high; the issue shows "fully reversed" while more came back than went
    out; reports inherit the error.

  RECOMMENDED SOLUTION
    1. Reversals: refuse the same issued line twice in one request (400); inside the
       transaction, lock the issue and its lines and re-check the remaining quantity there.
    2. Stock counts: refuse the same item + location twice in one request (400); read the system
       quantity inside the transaction from the locked stock row, so "counted" always becomes
       the final stock.
    3. Optional client: prevent adding a duplicate row in the stock-count form.

  ALTERNATIVES
    B. Merge duplicate lines automatically (add them up) instead of refusing.
       + no error for the user
       - for counts, two "counted 15" lines would mean 30, which is probably not what the user
         meant; silent guessing is risky

  ADVANTAGES
    Stock counts always land exactly on the counted value; reversals can never exceed issues.
  DISADVANTAGES
    Users who listed an item twice get an error and must combine the lines.
  SIDE EFFECTS
    A count that runs at the same time as another movement now uses the up-to-date stock (this
    is more correct, but means the "system quantity" shown may differ from the one on screen).
  DECISION
    None.
  DATA CHECK
    SELECT id, asset_issue_id, issued_quantity, reversed_quantity FROM asset_issue_items
     WHERE reversed_quantity > issued_quantity;
  TESTING
    Duplicate-line reversal -> 400 with stock unchanged; duplicate-line count -> 400; normal count
    lands on the counted value; 4 parallel full reversals -> exactly one succeeds; full regression.

 D-01 — Registration and chassis numbers are unique across ALL organizations
   Background : the client asked for this in Phase 3 (database triggers, migrations 0016 and
                0063). The specification asks for uniqueness per organization.
   Effects    : - one organization can learn that another already has a given registration
                  (it gets "already in use")
                - an ARCHIVED vehicle blocks its number for every organization forever: a
                  vehicle sold by one organization can't be registered by the buyer (the

   Options    : keep / exclude archived vehicles from the check (restore must then re-check) /
                return to per-organization uniqueness
   Recommend  : confirm with the client.  Baseline tests: 1 (written for "exclude archived").

 D-02 — A stock count can't add stock to an item with zero stock at the site
   stockAdjustment.service.js:132 refuses a count when the site has none of the item, so
   opening stock or found items can only enter through a purchase.
   Recommend  : allow it (counts are the usual way to load opening stock).

 D-03 — Login, forgot-password and reset share one rate limit per network address
   200 attempts per 15 minutes in development, 20 in production. Many failed logins from an
   office network also block password resets for everyone there.
   Recommend  : optional; separate limits if offices share one internet address.

====================================================================================================
 PART 9 — GLOSSARY
====================================================================================================
  400 / 403 / 404 / 409 / 500
      Response codes: bad input / not allowed / not found (or another organization's record) /
      conflict with current data / server crash.
  Transaction
      A group of database changes that succeed or fail together.
  Row lock (SELECT ... FOR UPDATE)
      Makes other requests wait until this transaction finishes using that row.
  Race condition
      Two requests at the same moment both pass a check that only one should pass.
  Deadlock
      Two requests each wait for the other forever; MySQL kills one, which surfaces as a 500.
  Migration
      A numbered script that changes the database structure; it can be applied (up) or undone
      (down).
  Regression
      Something that worked before and breaks because of a change.
  Tenant / organization
      One customer company; its data is fully isolated from other organizations.
  Archive
      Soft delete: the record is hidden but kept, and can be restored.
  FIFO / oldest-first costing
      Stock leaves at the cost of the oldest batch first.
  Fuzzing
      Sending many malformed values automatically to find crashes.
